# Tools & Guides Editorial Orchestrator

This skill implements the **v3 practice revision** of `docs/editorial/TOOLS_AND_GUIDES_ORCHESTRATOR_V1.md` (stable file path for the existing Tuesday/Friday task). **Read the latest version on the default branch first**, followed by `TOOLS_AND_GUIDES_V1.md`, `TOOLS_AND_GUIDES_TEMPLATES_V1.md`, `docs/editorial/tools-and-guides/LEDGER_V1.md`, all merged evergreen ledgers, the visual constitution, current guide schema and relevant Astro pages. This skill may be called by the independent twice-weekly ChatGPT scheduled task or explicitly by a maintainer.

## Workflow

Apply the canonical **Editorial Voice v2** section of `TOOLS_AND_GUIDES_V1.md`: direct, approachable, independently skeptical and evidence-led. Choose the editorial genre before outlining; comparisons, investigative analysis and practical explainers share a voice, not a heading sequence. Templates are optional worksheets. Keep `format` within `tutorial`, `review`, `toolkit`; express genre in prose. Use a duplication matrix for an explicitly commissioned series, without changing the scheduled one-guide/one-PR limit.

1. Inspect current GitHub `main`, **all existing Tools & Guides ledgers**, open guide/ledger-only PRs (including their unmerged ledger changes), published and unpublished guides, especially the already-published first RAG deployment and retrieval-evaluation tutorials. Do not assume only merged documents exist; never invent a branch or assume old snapshots are current.
2. Before drafting, perform the four capability checks in the canonical contract (generation, image inspection, WebP conversion, binary upload). Record observed evidence; exposed tool names alone do not prove successful production. If unavailable or unverified, preserve work only as a blocked draft with exact stage/error and recovery. Resume an existing incomplete guide PR before selecting a new topic, including on a later date; retain its original branch, ledger date and PR number. Never infer that tools available in an interactive session exist in the scheduled runtime.
3. Find a meaningful evergreen engineering question. Deduplicate by stable `topic_key` and by **reader problem, intended outcome, audience and scope**, not merely matching titles. Record selected/watch/rejected/duplicate/material-update decisions with reasons and actual related guide/PR identifiers. Prefer existing work and substantive updates over near-duplicates. No mandatory quota.
4. Collect verified primary sources and an editorial evidence table: claim, reference URL, observed date, verified or unverified, implications. Ensure source links exist and directly support claims.
5. Plan content using the matching template. For tutorials, require (a) a clear learning outcome, (b) **rendered, accessible technical SVG diagram** with accurate labels, desktop/mobile legibility, alt text and explanatory prose, (c) fully copyable, language-tagged code/commands **within the Markdown guide**, (d) testing and observable results or explicit “not executed”, (e) failure recovery, costs, security and privacy, and (f) citations to original documentation.
6. **Curate optional related reading within the guide draft.** Read `docs/editorial/RELATED_READING_V1.md` when present. Inspect existing published guides by the concrete reader outcome, not matching names or tags. Add zero to three `relatedGuides` entries (`id`, `reason`) to the new guide's own frontmatter; never edit news or the legacy mapping file. Record selections with reasons, or a deliberate zero-match, in the PR. Recheck destinations before the later separately authorized publication.
7. **Two separate visual roles:** the cover is a high-resolution, wordless **WebP editorial illustration** in `public/images/guides/`, generated to the `VISUAL_CONSTITUTION_V1.md` metaphor/materiality rules. Compare against at least two production-reference images, check article/card/mobile crops, record real provenance and commit via binary-safe upload with a matching accessible `imageAlt`. No SVG cover, schematic, fake interface or invented claims. The teaching diagram is a separate **rendered, labeled SVG** (prefer desktop/mobile variants) that accurately maps the code, with alt text and prose. A bare ASCII fence or unrendered Mermaid block does **not** satisfy this diagram requirement. Persist artwork state (`pending`, `generated`, `reviewed`, `uploaded`, or `blocked`) and stage evidence in the evergreen ledger using LEDGER_V1.md. An error sets `blocked` with exact stage/message/recovery while retaining successful earlier-stage evidence. If tooling or review prevents either asset, keep the guide draft and mark `handoff.completion: blocked`; never forge visual evidence.
8. Keep scope to the article, its guide-specific artwork and diagrams, and the separate `docs/editorial/tools-and-guides/ledgers/YYYY-MM-DD.json`. Do not add an `examples/` app, article-specific CI regression suite/job, new hosting service or generic frontend feature for an ordinary guide. Read and follow `docs/editorial/tools-and-guides/LEDGER_V1.md`; retain at most one selected/material-update candidate per run and prevent repeat draft selections. Check an existing `content/tools-guides-YYYY-MM-DD` branch/PR before writing. Limit to one **draft** PR per execution. A meaningful ledger-only draft PR is permitted without a guide, not an empty filler PR. No **news** ledgers, daily issues, publication scheduler or unrelated frontend additions.
9. Verify every real executed command; distinguish verified output, illustrative output and untested integration. Keep code self-contained in article Markdown and use `verification: researched` unless the schema's full `hands-on` evidence exists. Never invent a byline, reviewer or approval; **reviewer is optional**. Leave `status: draft` for the scheduled PR and explicitly state remaining gates. Only a subsequent human-authorized publication change may set a real `publishedAt`, required metadata and `status: published`.
10. Write the current editorial date's ledger for new work, or update the original unmerged ledger and branch when resuming a blocked PR. Validate with `npm run guides:ledger:check` and, for validator changes, `npm run guides:ledger:test`. Run available **existing** `npm run verify` and relevant browser/e2e checks, and inspect the exact commit's GitHub Actions run. Verify source/image paths and that drafts are intentionally absent from public listings; after a separate authorized publication and deployment, verify the live `/guides/` listing and detail route. If a check cannot be run or fails, report that, not success. Do not mark ready, merge or publish autonomously.

## Handoff

Start the report with `Blocked — resume PR #N` whenever artwork or any other preparation gate is incomplete, even if CI is green. Claim a complete handoff only with uploaded, reviewed, integrity-verified WebP, matching `image`/`imageAlt`, all other preparation gates passed and exact-head CI green. A complete handoff still needs human publication approval. On a later trigger, continue the original PR and update its unmerged ledger; do not generate replacement artwork when the inputs and valid existing asset are unchanged.

Return a concise report: date and canonical topic key; selected/watch/rejected/duplicate/material-update decisions; current ledger path and **persistence state** (merged/open PR/not persisted); duplicate comparisons to published guides and open PRs; sources; verification and limitations; diagram check; artwork check; branch and PR URL (if created); CI; blockers; whether the guide is visible publicly (**it should not be while draft**). If no viable content or required tools, return a truthful no-publication or blocked report without creating filler.

No schedule is defined by this skill: the ChatGPT task owns Tuesday/Friday recurrence. No external VPS, additional subscription, paid API or independent orchestrator service is required by design.
