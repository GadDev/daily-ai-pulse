La manière la plus sûre de laisser un agent créer une interface consiste peut-être à l’empêcher de fabriquer directement l’interface.

A2UI 1.0, première version stable du protocole ouvert d’interface générative de Google, permet à un agent de décrire une vue à l’aide de composants enregistrés. L’application hôte les affiche avec son moteur natif. Le modèle n’a pas besoin de rédiger du HTML arbitraire, de livrer un bundle JavaScript ni de recevoir toutes les valeurs sensibles à l’écran.

Cette séparation est le produit.

## Ce qui change

La version 1.0 apporte un protocole stable, des appels de fonctions bidirectionnels, des métadonnées d’accessibilité et des points d’extension. Les moteurs de rendu open source couvrent React, Angular et Lit sur le Web, Flutter sur plusieurs plateformes, SwiftUI sur iOS et Jetpack Compose, qui passe encore de 0.9.1 à 1.0.

Des SDK d’agents existent pour Python, TypeScript et Dart. A2UI peut aussi s’afficher dans des MCP Apps, de sorte qu’une même vue décrite par un agent soit intégrée à des assistants compatibles comme Claude et Gemini.

Google cite plusieurs utilisateurs. Atlassian propose des cartes interactives lorsqu’un agent a besoin d’une décision dans un ticket Jira. Alation affiche des flux de données et des graphiques dans son application et dans Claude. ByteDance dispose d’un moteur A2UI pour Lynx et l’adapte à la version 1.0.

Ces exemples prouvent un travail d’intégration. Ils ne valident pas indépendamment les affirmations générales de Google sur la latence, la fiabilité ou la sécurité.

## Le protocole limite l’autorité du modèle

Une interface entièrement générée par un modèle peut inventer des commandes, introduire des données sensibles dans les prompts ou proposer une action dont l’utilisateur ne comprend pas les conséquences.

A2UI renvoie des choix importants au code applicatif. L’hôte enregistre les composants autorisés, contrôle leurs liaisons aux données, peut conserver les valeurs sensibles côté serveur et décide de la signification et de l’autorisation d’un appel de fonction.

C’est plus solide que de demander au modèle de produire du code frontend sûr à chaque interaction. Ce n’est pas automatiquement sûr.

Un modèle peut encore choisir un composant trompeur, omettre un avertissement, présélectionner une option ou réclamer une fonction lourde de conséquences. Un moteur de rendu peut mal implémenter le protocole. Une extension peut élargir la surface d’attaque.

La vraie frontière de sécurité réside dans la liste des composants autorisés, la validation des schémas, les liaisons côté serveur et les règles d’action, pas dans le nom du protocole.

## Les appels bidirectionnels méritent le plus d’attention

La version 1.0 permet à une vue générée d’appeler des fonctions, par exemple vérifier une disponibilité depuis un sélecteur de réservation.

C’est utile, mais cela relie l’affichage à l’action.

Chaque fonction devrait disposer d’un schéma d’entrée explicite, d’une vérification d’autorisation indépendante et d’une règle de confirmation claire. L’utilisateur doit voir ce qui va se produire avant l’envoi de données ou la modification d’un état. L’application doit distinguer consulter de réserver, rédiger d’envoyer et proposer d’approuver.

Une fonction appelée depuis un composant natif n’est pas pour autant autorisée : c’est toujours l’agent qui a choisi et rempli ce composant.

## Ce que les équipes devraient tester

Créez un workflow limité avec un petit catalogue de composants, puis examinez les cas difficiles :

- composants inconnus et extensions non prises en charge ;
- charges utiles invalides ou trop volumineuses ;
- données serveur obsolètes ;
- ordre de lecture accessible pendant les mises à jour diffusées ;
- actions demandées avant la confirmation requise ;
- même message rendu dans deux clients différents ;
- clients plus anciens limités à la version 0.9.1 ;
- texte hostile dans les champs de données.

Conservez le message du protocole, la version du moteur de rendu, le composant choisi, les valeurs affichées et l’appel de fonction résultant. Une capture d’écran ne permet pas à elle seule d’auditer une décision interactive prise par un agent.

## L’avis de Pulse

A2UI est prometteur parce qu’il oblige le modèle à parler un langage d’interface limité plutôt qu’à recevoir les clés du navigateur.

La version stable donne enfin aux équipes quelque chose de concret à mettre en œuvre et à tester entre plusieurs hôtes. Le travail difficile reste magnifiquement traditionnel : schémas, permissions, confirmations, compatibilité et rendu accessible.

Ce n’est pas une critique. Les interfaces agentiques ont besoin de davantage de contrats ennuyeux et de moins de démonstrations magiques.
