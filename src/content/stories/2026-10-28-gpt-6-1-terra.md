OpenAI has released GPT-6.1 Terra in the API, ChatGPT Work and Codex. The company positions it as a lower-cost option for computer use, visual reasoning and other high-volume workloads. Its posted standard API prices are $1 per million input tokens, $0.05 per million cached input tokens and $5 per million output tokens.

Those prices are concrete. The performance, factuality and safety comparisons published alongside them are OpenAI's own evaluations. No independent production comparison was available in this edition's reporting window, so the release changes the routing options engineers can test—not what they can safely assume.

## What changed

The important change is not another benchmark row. A model with computer-use support is now available at a lower posted token price than OpenAI's larger GPT-5.6 Terra and GPT-6.1 Sol options. That creates a plausible new route for visual inspection, browser interaction and repetitive agent tasks where volume makes model cost visible.

OpenAI also published release notes and a safety evaluation addendum. Those materials provide first-party evidence for availability, pricing and the company's test results. They do not establish how Terra behaves inside a particular browser harness, against private documents or under an organization's own acceptance criteria.

## The routing decision is larger than token price

A cheaper call can still produce a more expensive task. If a route fails validation, requires a stronger-model retry or sends a human back through the work, the first call becomes overhead. Computer-use workflows add more variables: screenshots, tool latency, repeated observations and the risk that a superficially successful action changed the wrong thing.

Measure the full unit of work instead:

- accepted tasks per route;
- retries and escalation rate;
- median and tail latency;
- input, cached-input and output usage;
- human-review time;
- failures that pass automated checks but miss the intended outcome.

This is why the posted prices should trigger an evaluation, not an automatic migration. The engineering question is whether Terra lowers cost per accepted task while staying inside the same quality and safety boundary.

## A practical evaluation

Start with a small replay set drawn from real work. Include ordinary cases, visually ambiguous states, interrupted sessions and tasks that should be refused or escalated. Freeze the initial state when possible, record the model and tool trace, and define success before running the comparison.

Route the same cases through the current model and Terra. Keep the browser harness, validation rules and retry policy fixed. Report both the first-attempt result and the final result after escalation. Otherwise, a router can look inexpensive simply because the cost of its failures is charged to another model.

For actions with side effects, keep human confirmation or an equivalent policy boundary until the evaluation shows that the cheaper route meets the same acceptance conditions. A vendor benchmark cannot substitute for an application's authorization model.

## Pulse take

This is a useful release because it makes a familiar systems question unavoidable: which model is good enough for this particular path, and how will you know? The interesting number is not $1 per million input tokens. It is the cost of the task after validation, retries and review.

Do not rewrite a production router from the launch post. Add Terra as a measured candidate, preserve escalation, and let task-level evidence decide whether it earns traffic.
